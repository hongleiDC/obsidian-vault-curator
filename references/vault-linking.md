## 1. 为什么先索引

没有 Vault 上下文时，模型不能可靠知道 `[[某概念]]` 是否真实存在。批量整理前先建立索引，避免：

- 指向不存在笔记的假双链；
- 文件 stem 重名导致的错误解析；
- heading / block link 指向不存在目标；
- 改标题后破坏其他笔记的入链；
- 在不同目录重复创建同义标签。

## 2. 建立索引

运行：

```bash
python scripts/build_vault_index.py /path/to/vault --output /tmp/vault-index.json
```

索引包含：
- Markdown 相对路径；
- 文件 stem 与首个 H1；
- headings；
- block IDs；
- 已有 wikilink targets；
- embeds；
- 重复 stem 列表。

`.obsidian`、`.git`、`.trash`、`node_modules` 默认跳过。

## 3. 链接置信度规则

只在满足以下至少一个条件时新增链接：

- 当前术语与真实存在的目标笔记标题/stem 明确一致；
- 当前句子明确讨论目标笔记的核心主题；
- 用户明确要求把两篇笔记关联；
- 现有 Vault 已经形成稳定命名模式，当前链接明显延续该模式。

不要因为两个词“看起来相关”就建链。

链接密度：
- 同一段通常不重复链接同一个目标；
- 同一概念在一篇笔记里通常首次或最关键处链接一次即可；
- 链接应帮助导航或理解，而不是增加 Graph View 边数。

## 4. 重复文件名

如果索引显示两个或更多 Markdown 文件具有相同 stem：

- 不使用含糊的 `[[SameName]]` 新链接；
- 使用能唯一解析的相对路径形式，例如 `[[folder/SameName]]`；
- 如果用户已有别名习惯，可用 `[[folder/SameName|显示名]]`；
- 不自动合并重名笔记。

## 5. Heading 与 block link

新增：

```markdown
[[Note#Heading]]
[[Note#^block-id]]
```

之前必须确认：
- 目标笔记存在；
- Heading / block ID 在目标笔记中存在；
- 目标足够稳定，值得使用深链接。

如果只有主题级关联，优先 `[[Note]]`，不要无必要使用脆弱的 heading link。

## 6. 标签治理

批量任务先统计已有标签再补充。

优先级：
1. 复用已有稳定标签；
2. 合并仅大小写或轻微拼写不同的重复标签；
3. 新增极少量高价值父/子标签；
4. 不建立大而全的自动 taxonomy。

若用户已有 PARA、Zettelkasten、Johnny Decimal、MOC 或自定义分类体系，先遵循原体系。

## 7. 文件重命名与移动

普通整理禁止自动重命名/移动。

用户明确要求时：

1. 用索引找到所有可能引用该笔记的 wikilink / embed；
2. 检查重名冲突；
3. 执行移动或重命名；
4. 同步更新受影响链接；
5. 再次建立索引确认没有新断链。

不要假设 Obsidian 客户端会替你自动更新链接，因为 Skill 可能在客户端之外修改文件。

## 8. 批量整理策略

不要“一次性重写全库”。按以下顺序：

1. 选定目录或主题簇；
2. 建索引；
3. 抽查 2–5 篇代表性笔记，确定风格；
4. 批量应用同一整理原则；
5. 再做跨笔记链接和标签治理；
6. 运行保护验证；
7. 最后检查 orphan / broken link / duplicate stem 的变化。

对于内容差异很大的 Vault，不强求所有笔记使用同一模板。

## 9. 大型 Vault 的停止条件

当出现以下情况时停止自动扩张，优先交付可验证的小批次：

- 上千篇笔记且命名体系不稳定；
- 多个插件生成大量机器维护字段；
- 存在大量重复 stem；
- 笔记跨多语言且 aliases 体系不明确；
- 用户没有要求统一 taxonomy，却出现大量潜在标签变更；
- 链接目标无法可靠唯一解析。

此时先完成已选范围，并报告需要用户决定的治理问题；不要猜测全库策略。
